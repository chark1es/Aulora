# Deploy on Coolify

[Coolify](https://coolify.io) runs the Aulora stack from this Git repository and
terminates TLS for you with its Traefik proxy. Aulora ships a Coolify-ready
compose file, `infra/docker/docker-compose.coolify.yml`. Use it instead of
`docker-compose.yml`: it publishes no host ports, keeps the generated secrets in
a named volume so redeploys do not regenerate them, and marks the one-shot
services so they do not fail Coolify's health check.

## Before you start

- A Coolify instance (any recent v4) with a server attached.
- Two DNS names pointed at that server, for example `chat.example.com` (the app)
  and `convex.example.com` (the Convex API and WebSocket).
- The owner email and a password of at least 32 characters.

## 1. Create the resource

In Coolify, create a **new resource → Docker Compose** (Git-based) and point it
at this repository, then set:

| Field | Value |
| --- | --- |
| Repository | this Git repository |
| Branch | the branch you deploy (for example `main`) |
| Base Directory | `infra/docker` |
| Compose Location | `docker-compose.coolify.yml` |
| Preserve Repository During Deployment | **on** |

**Preserve Repository during deployment** is required: the stack bind-mounts
repo-relative paths (`./initdb`, and `./vault` if you enable the optional `ekm`
profile) and Coolify otherwise deletes the checkout after deploying. With the
toggle on, those files exist when the containers start.

## 2. Set the environment

Open the resource's **Environment Variables** and paste the values below
(Coolify's developer view accepts `KEY=value` lines). They are the operator
values from `infra/docker/.env.example`; see that file for the full annotated
list.

```sh
INSTANCE_NAME=aulora
WORKSPACE_NAME=Aulora
OWNER_EMAIL=owner@example.com
OWNER_PASSWORD=change-me-please-32-chars-min
OWNER_NAME=Aulora Owner

# Public origins — must match the domains you add in step 3.
SITE_URL=https://chat.example.com
CONVEX_CLOUD_ORIGIN=https://convex.example.com
CONVEX_URL=https://convex.example.com
CONVEX_SITE_ORIGIN=https://chat.example.com
TRUSTED_ORIGINS=https://chat.example.com

# Postgres and object storage (change the passwords for a real deploy).
POSTGRES_USER=convex
POSTGRES_PASSWORD=aulora-postgres
POSTGRES_URL=postgresql://convex:aulora-postgres@postgres:5432
MINIO_ROOT_USER=aulora
MINIO_ROOT_PASSWORD=aulora-minio-secret
```

You can leave the generated secrets blank and let `setup` create them, but on
Coolify it is safer to set them explicitly in this list so they are stable
across deploys. Generate each once and keep the values:

```sh
# 32-byte base64 master key: the KEK, root of data confidentiality.
openssl rand -base64 32      # -> AULORA_ENCRYPTION_KEY
openssl rand -base64 48      # -> BETTER_AUTH_SECRET
openssl rand -hex 32         # -> INSTANCE_SECRET
```

Set `AULORA_ENCRYPTION_KEY`, `BETTER_AUTH_SECRET` and `INSTANCE_SECRET` to those
values. Web-push keys (`VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`) are generated by
`setup` and kept in the volume; add them here too if you rotate them.

> **Never paste these into a public place, and never delete the volume that
> holds them.** If `AULORA_ENCRYPTION_KEY` changes, existing messages and files
> become unreadable ciphertext.

## 3. Add two domains

On the resource's **Domains**, add:

| Domain | Service | Container port |
| --- | --- | --- |
| `https://chat.example.com` | `web` | `80` |
| `https://convex.example.com` | `convex-backend` | `3210` |

Coolify's proxy terminates TLS, so `SITE_URL` and `CONVEX_CLOUD_ORIGIN` must
match these two domains exactly.

`/api/auth/*` must stay on the **web** domain. The browser calls it there so the
Better Auth session cookie is first-party; the `web` nginx container proxies it
to the Convex HTTP-actions port (`convex-backend:3211`) internally. Do not add an
`/api/auth` route to the Convex domain, and set `CONVEX_SITE_ORIGIN` to the web
origin (as above). The Convex backend fetches
`https://chat.example.com/api/auth/convex/jwks` to validate its own tokens, so
both DNS names must resolve publicly.

Only `web` and `convex-backend` need a domain. Postgres, MinIO, the dashboard
and the push relay stay on the internal Docker network.

## 4. Deploy

Press **Deploy**. Coolify builds `web` and `setup` from the repository, starts
the stack, and runs the one-shot `setup` service. `setup` mints the admin key,
creates the workspace and owner, deploys the Convex functions, and writes the
public `/.well-known/aulora.json`. It is idempotent and safe on every deploy.

To watch it, open the `setup` service logs (or the deployment logs) and wait for
`[setup] done`. Then open `https://chat.example.com` and sign in as the owner.

To re-run `setup` after changing auth providers or `TRUSTED_ORIGINS`, redeploy the same Coolify resource.

This file uses Coolify-specific `exclude_from_hc` fields. Plain Docker Compose rejects the raw source file. If using host commands, use Coolify's rendered Compose configuration and its existing project/environment, not the source template. See [Coolify's Compose documentation](https://coolify.io/docs/applications/builds/docker-compose).

## How the generated secrets persist

On a normal `docker compose` install, `setup` writes generated secrets to
`infra/docker/.env`, and Compose re-injects them through `env_file` on the next
run. Coolify does not provide that file, so this stack keeps them in the
`setup-state` named volume instead (`setup` writes `/host/.env`, the same path,
and re-reads it each run). A redeploy therefore reuses the same
`INSTANCE_SECRET`, `BETTER_AUTH_SECRET` and VAPID keys — and, when you did not
set it yourself, the same generated `AULORA_ENCRYPTION_KEY`.

Do not delete the `setup-state` volume, and keep an offline copy of
`AULORA_ENCRYPTION_KEY`: encrypted content in the database and exports needs that key to be readable. Other metadata may remain readable. The same warning as
[Self-hosting → Encryption](self-hosting.md) applies.

## Screen streaming

Streaming a desktop or an application to many people uses the bundled LiveKit server, which this resource runs and configures for you. It creates its own keys, `setup` hands them to Convex, and clients reach it at your web domain under `/livekit`, so there is nothing to set and no third domain to add. The only step Coolify cannot do is open the media ports: allow `7881/tcp` and `7882/udp` to the server in its firewall. Until you do, shares still work, sent directly to each viewer instead. Behind NAT, see [Self-hosting](self-hosting.md#screen-streaming-server-optional).

## Optional services

The backup runner, push relay, and development Vault have Compose profiles and are off by default. To enable an optional service in this resource, remove its `profiles` entry in your deployment branch and redeploy the same Coolify resource. Configure its environment values in Coolify first. Keep the project and named volumes unchanged so the service joins the existing deployment.

Do not create a second independent stack for backups; it would have different named volumes and could back up a fresh deployment instead. If managing profiles through host commands, use Coolify's rendered configuration, project name, and environment.

- Backups require a working destination and an off-machine copy; see [backups](backups.md).
- Mobile push requires relay authentication and publisher APNs/FCM credentials.
- The bundled Vault runs in memory for development. Use a persistent external key manager in production.

## Upgrade

Redeploy the resource (Coolify pulls the branch and rebuilds `web` and `setup`).
The named volumes, including `setup-state`, are kept, so data and secrets
survive. If you changed origins or auth settings, re-run `setup` as above.

To install published releases directly from the instance admin panel, set these runtime environment variables on the same Coolify resource:

```sh
AULORA_COOLIFY_URL=https://coolify.example.com
AULORA_COOLIFY_APPLICATION_UUID=your-application-uuid
AULORA_COOLIFY_API_TOKEN=your-api-token
```

Use the UUID of this Git-based Docker Compose **application**, not a service or server UUID. Create an API token in Coolify's **Keys & Tokens** with permission to read the application and deployments, update the application, and deploy it. The Coolify URL must be reachable from the Convex backend. Keep the token out of build variables and client configuration.

Redeploy once to apply this configuration through `setup`. The shipped Compose file selects the Coolify update provider automatically. The instance panel then offers **Install update**. It resolves the published Git tag to an immutable commit, pins the application's `git_commit_sha`, and asks Coolify to build and deploy it. Status is tracked through the Coolify API; success requires the backend to run the requested version. Deployment briefly interrupts the workspace. A failed installation reports an error and can be retried after checking the Coolify deployment and setup logs.

The application stays pinned to the installed commit. To resume deploying your branch manually, reset `git_commit_sha` to `HEAD` in Coolify. The integration verifies that the application's GitHub repository matches `AULORA_UPDATE_GITHUB_REPO`, which defaults to `chark1es/Aulora`.

Without API configuration, the panel still checks for releases and explains which settings are missing. Apply releases manually through Coolify. Do not run `infra/docker/update.sh` inside Coolify's source directory.

## Teardown

Stop or delete the Coolify resource. **Deleting the volumes wipes the data and
the generated secrets, irreversibly.** If you want to keep the deployment
recoverable, back up `AULORA_ENCRYPTION_KEY` and the database first
(see [Backups](backups.md)) before removing the `pgdata`, `convex-data`,
`minio-data` and `setup-state` volumes.

## Troubleshooting

- **Login redirects but the session does not stick** — `/api/auth/*` is not
  same-origin. Check that `CONVEX_SITE_ORIGIN` equals `SITE_URL` and that no
  `/api/auth` route was added to the Convex domain.
- **`setup` keeps failing the deployment health check** — the one-shot services
  must carry `exclude_from_hc: true`; keep that key when you edit the file.
- **Data unreadable after a redeploy** — `AULORA_ENCRYPTION_KEY` changed. Restore
  it from your backup and point the stack at the original value; the ciphertext
  cannot be recovered without it.
- **WebSocket or API errors from the client** — `CONVEX_CLOUD_ORIGIN` must be the
  public Convex domain and must not have a trailing slash.
