Backups and restore

3 min read

A useful backup must include deployment data, uploaded files, and the original encryption key. Keep the key separately and securely. Test a restore before relying on a backup.

Message bodies and uploads are encrypted by default, but account and other metadata can remain readable. Treat every backup as sensitive. Raw Postgres dumps can also include backend deployment configuration; do not assume they exclude encryption credentials.

Enable nightly backups

From infra/docker:

sh
docker compose --profile backups up -d --build
docker compose logs --tail=100 backup

The runner exports the Convex deployment with --include-file-storage, takes a Postgres dump, writes a non-secret encryption manifest, and uploads the artifacts to backups/<timestamp>/ in the configured bucket. It records the result in Instance admin.

The default bucket is in the same MinIO installation as the live data. That is a local copy, not disaster recovery. Copy backups to separate storage or configure an off-machine destination. Verify that the copy includes convex.zip, postgres.dump, and encryption.json.

For a one-off backup:

sh
docker compose --profile backups run --rm -e BACKUP_RUN_ONCE=1 backup

Pass container settings with -e. Prefixing a Compose command with a shell variable does not automatically pass that variable to the container.

Configuration

VariableDefaultMeaning
BACKUP_HOUR_UTC3Nightly start hour, 0 through 23 UTC
BACKUP_ENABLEDtrueSet false to idle the runner
BACKUP_BUCKETaulora-backupsDestination bucket
BACKUP_RETENTION7Number of local run directories to retain
BACKUP_TOKENGenerated by runnerAuthenticates result recording
BACKUP_RUN_ONCEUnsetPass 1 to run once and exit
BACKUP_SKIP_UPLOADUnsetPass 1 for a local-only test

Local pruning does not delete remote objects. Configure remote bucket lifecycle rules separately. A failed result-recording request does not mean the backup itself failed; inspect the runner log and actual artifacts.

Securely back up infra/docker/.env separately. It includes INSTANCE_SECRET, AULORA_ENCRYPTION_KEY, and authentication/storage configuration. For an external key manager, also preserve access to the original KEK and all key versions needed by historical content. encryption.json contains no key material.

Restore a Convex snapshot to an isolated stack

Use a separate machine or a Compose project with its own ports and volumes. Never test by overwriting the live workspace. Start from the same Aulora revision and pinned backend images as the backup, then upgrade after recovery.

Restore the private .env before starting the new stack. Preserve the original encryption key, instance identity, and secret. Adjust public origins, project name, and ports for the isolated environment. Start the stack and allow setup to finish.

Download the backup's convex.zip into an infra/docker/restore directory on the recovery host. From infra/docker, run:

sh
docker compose run --rm \
  -v "$PWD/restore:/restore:ro" \
  --entrypoint bash setup -lc '
    set -euo pipefail
    cd /app/packages/convex
    export CONVEX_SELF_HOSTED_ADMIN_KEY="$(generate_key "$INSTANCE_NAME" "$INSTANCE_SECRET")"
    bunx convex import --replace-all --yes /restore/convex.zip
  '
docker compose run --rm setup

The snapshot filename is a positional argument, not --path. The mount makes it available inside the container. --replace-all replaces deployment data, so use it only on the recovery instance. On Windows, use PowerShell's multiline syntax and an absolute host path for the mount, or run these shell commands in WSL.

Do not also apply postgres.dump after importing the logical snapshot. They are alternative recovery methods. Raw Postgres recovery additionally requires the matching backend files/object-storage state and service shutdown coordination; it is an advanced infrastructure recovery procedure rather than this portable snapshot restore.

Verify recovery

Sign in with an account from the backup. Read old channel and direct messages, check memberships and permissions, and download attachments uploaded before the backup. Confirm the original encryption key is still configured.

Record the snapshot time, successful restore time, and data you checked. Rotate access credentials as appropriate after recovery without destroying the content-encryption key. Resume backup scheduling only after verification.
